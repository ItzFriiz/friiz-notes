# 认知文档维护方法

认知文档记录有反馈依据的知识基础、阅读偏好与理解障碍，用来决定下一次写作如何调整。它不评价整体能力，也不充当逐轮聊天日志。

## 记录格式

| 字段 | 记录内容 |
| --- | --- |
| 观察 | 已表现出的知识基础、阅读偏好或具体理解障碍 |
| 依据 | 用户明确反馈及得到认可的修订，优先用短摘要 |
| 适用范围 | 哪些主题或问题适用，哪些尚未确认 |
| 写作决策 | 下次因此保留、补充、压缩或重排什么 |

[脱敏示例](learner-model.md) 展示这种格式。公开示例不能当作当前用户的特征。只保留会影响后续写作的记录，不把一次困难概括为能力不足，不把没有异议当作理解确认。

## 读取与更新

- 公共安装版的实际记录放 `references/learner-model.local.md`，该文件被 Git 忽略；尚未建立时依据当前反馈和已有正文判断，不套用示例。
- 写作与独立审查前读取实际记录，以及当前课程／项目的 `NOTE_RULES.md`。当前明确反馈和正文已建立的知识优先于旧记录；审查者应收到实际记录的路径或所需摘录。
- 用户审查笔记后，只有在明确要求更新认知文档时才修订。合并重复条目，依据新证据修正旧结论，不自动积累推测。
- 跨主题的理解方式放认知文档；特定主题的知识状态放当地私有规范，不推定到其他领域。

## 需要 Git 版本历史与跨设备迁移时

可以使用一个本地仓库的 `private`、`public` 两个分支，分别连接私有与公开远端。GitHub 的可见性按整个仓库设置，不能让同一远端仓库的分支分别公开和私有；两个远端仓库仍需分开。

将完整 `private` 分支安装在 `~/.codex/skills/friiz-notes`，实际认知记录纳入该分支的 Git，并让入口和审查规则明确读取它。将 `public` 分支以 worktree（同一仓库另一分支的工作目录）放在 `skills` 之外，例如 `~/.codex/public/friiz-notes`；不要在安装目录切到公开分支。

通用规则在私人工作目录编写一次，再将同一份改动应用到公开分支，不重新撰写；保留各自的入口与认知文档。纯通用提交可以 cherry-pick，即将该提交的改动应用到另一分支；混合提交只移植可公开部分，不合并完整私人分支。真实反馈、主题知识状态、研究细节和可识别路径只留在私人分支；公开示例单独维护，不自动从实际文档生成。

提交与推送分别处理两分支，检查公开文件及待推送历史；只有私人改动时，无需公开提交。为两个远端设置明确的分支推送范围，不使用全分支或镜像推送。推送钩子可以核对目标、可见性及是否混入私人提交，但不能替代公开内容审查。

新设备从私有远端克隆完整安装版，再从公开远端恢复公开分支及 worktree。共享推送钩子需通过绝对路径配置 `core.hooksPath`，使两个工作目录都执行它；该配置及远端推送规则不会随克隆恢复，需要按私人版迁移说明重设。
